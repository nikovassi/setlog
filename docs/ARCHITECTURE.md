# Setlog – architecture plan

## 1. Overview

Frontend-only PWA. No backend, no external database, no analytics.

```
React UI (pages, components)
   │  hooks (useLiveQuery – reactive reads)
   ▼
services/   ← all writes & business rules (workouts, sets, routines, import/export)
   │
   ▼
db/ (Dexie → IndexedDB)      utils/ (pure math: volume, e1RM, PRs, progression)
```

* **UI never writes to Dexie directly** – it calls `services/*`. This keeps
  transactions, denormalised fields and validation in one place and makes the
  services unit-testable with `fake-indexeddb`.
* **Reads are reactive** via `dexie-react-hooks`-style `useLiveQuery` (a tiny
  in-house hook), so History/Progress update the moment a workout is finished.
* **Pure calculations** (`utils/calc.ts`, `utils/pr.ts`, `utils/progression.ts`)
  have no DB access → trivial to test.

## 2. Stack

| Concern | Choice | Why |
|---|---|---|
| UI | React 19 + TypeScript | Requested, stable |
| Build | Vite 8 | Fast, correct relative `base` handling |
| DB | Dexie 4 on IndexedDB | Versioned schema + upgrade hooks, transactions |
| Routing | React Router (HashRouter) | GitHub Pages has no SPA fallback; hash URLs survive refresh and deep links under `/setlog/` with no 404 trick |
| Charts | Recharts, **lazy-loaded** | Only the Progress / Exercise screens pay for it |
| Styling | Plain CSS + design tokens (CSS variables) | Zero runtime, tiny, themeable (dark default) |
| PWA | vite-plugin-pwa (Workbox `generateSW`) | Precache of hashed assets, update prompt |
| Tests | Vitest + Testing Library + fake-indexeddb; Playwright e2e | |

No icon library and no web fonts: icons are inline SVG, text uses the system font stack.

## 4. IndexedDB schema (Dexie, DB name `setlog`, version 1)

| Table | Primary key / indexes | Fields |
|---|---|---|
| `exercises` | `id, name, muscleGroup, isCustom` | id, name, category, muscleGroup, equipment, notes, isCustom, createdAt, repMin?, repMax?, weightStep?, archived? |
| `workouts` | `id, date, status, startTime` | id, name, date (YYYY-MM-DD), startTime, endTime, duration (s), notes, status (`active`/`completed`), routineId? |
| `workoutExercises` | `id, workoutId, exerciseId` | id, workoutId, exerciseId, order, notes, supersetGroup? |
| `sets` | `id, workoutExerciseId, workoutId, exerciseId, timestamp` | id, workoutExerciseId, workoutId*, exerciseId*, setNumber, weight, reps, rpe, isWarmup, completed, timestamp, notes |
| `routines` | `id, name, updatedAt` | id, name, description, exercises [{exerciseId, sets, supersetGroup?}], createdAt, updatedAt |
| `settings` | `key` | key/value (theme, defaultRest, repMin, repMax, weightStep, autoRest) |

\* denormalised so "all sets of exercise X" and "all sets of workout Y" are a single indexed query.

**IDs** are random strings (`crypto.randomUUID`), so backups from different
devices can be merged without collisions. Seed exercises use stable ids
(`ex-bench-press`) so re-seeding is idempotent.

**PRs are computed, not stored.** Editing or deleting an old set can never leave a stale record.

### Migration strategy

* Every schema change adds `db.version(n+1).stores({...}).upgrade(tx => …)`;
  old versions are **never edited or removed**.
* Upgrades only add/transform data; destructive changes require an explicit
  migration that copies data first.
* `SCHEMA_VERSION` is written into every JSON backup; import runs the same
  normalisation so old backups stay importable.
* If opening the DB fails (blocked, quota, private mode), the app shows a
  readable error screen with *Retry* and *Export* hints instead of a blank page.

## 5. Main user flows

1. **Log a session (primary):** Home → *Start workout* → pick routine (or empty) →
   exercise cards with *Last time* + pre-filled rows → tap ✓ → rest timer starts →
   next row is already filled → … → *Finish* → summary → History/Progress update instantly.
2. **Add exercise mid-session:** *+ Exercise* → search / muscle filter → tap → card appears (with history).
3. **Superset:** card menu → *Superset with next* → A1/A2 labels.
4. **Fix a mistake:** tap any value to edit; swipe-free *delete* via row menu → *Undo* toast.
5. **Review:** History → workout → edit or delete; Exercise → history + charts.
6. **Backup:** Settings → Export JSON / CSV; Import JSON → preview → merge or replace (explicit confirmation).

## 6. MVP scope

**In:** exercise library + custom exercises, workouts, sets (warm-up, RPE, notes),
routines, supersets, last-time display, double-progression suggestions, PR detection,
rest timer, history with edit/delete + undo, exercise history with charts,
progress dashboard, JSON export/import, CSV export, dark/light theme, offline PWA,
GitHub Pages deployment.

**Later:** lb units, plate calculator, body measurements, muscle-group volume,
deload tracking, recommendations, wearables, optional encrypted cloud sync, accounts.

## 7. GitHub Pages decisions

* `base` is computed in `vite.config.ts` from `VITE_BASE` (CI sets it to
  `/<repo-name>/`, default `/setlog/`), so all asset URLs are prefixed – no `/assets/...`.
* The manifest uses **relative** `start_url`/`scope` (`./`) and icon paths, so it
  works under any sub-path.
* HashRouter → no server rewrites needed; refresh on any screen works.
* The service worker is registered with the base-relative scope and precaches
  the whole build, so the app opens offline after the first visit.
* `.github/workflows/deploy.yml`: checkout → `npm ci` → lint → unit tests →
  build → Playwright e2e against `vite preview` under the sub-path →
  `upload-pages-artifact` → `deploy-pages`. Any failure stops the deploy.
